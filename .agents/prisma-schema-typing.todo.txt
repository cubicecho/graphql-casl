Schema-driven condition typing (à la @casl/prisma) — exploration
================================================================
Status: NOT STARTED. Raised by user during the GraphQLAbility redesign.
Prereq context: GraphQLAbility redesign is DONE (see graphqlability.todo.txt).

CORRECTION (2026-08): this file was written against an intermediate design with
a bespoke conditions language (GqlOperators / GqlConditionsFor). That language
does NOT exist — GraphQLAbility is a CASL MongoAbility and conditions are CASL's
standard mongo-query operators, typed per subject via MongoQuery<TMap[K]>. Read
every "GqlOperators" below as "MongoQuery". This changes the premise of P2 and of
decision point 1: the operator set is CASL's, not ours, so making it field-type-
aware means diverging from CASL's matcher — a much larger commitment than
adjusting a hand-rolled type, and it would break the JSON round-trip with any
other CASL consumer.

The idea
--------
@casl/prisma derives per-model condition types from Prisma's generated
`Prisma.<Model>WhereInput` (rich filters: equals/in/gt/contains/...), via:
  - PrismaQuery<Model<User,'User'>>  -> the model's WhereInput as the condition type
  - createPrismaAbility               -> factory bundling the prisma conditions matcher
  - accessibleBy(ability).ofType('Post') -> rules folded into a Prisma where filter
The user asked: can we do the analogous thing for GraphQL — "take in the gql schema
so we can get the input types for the queries/mutations/etc"?

Where this maps onto our design
-------------------------------
- Condition VALUE types: we already derive them from the model (SubjectMap from
  ResolversTypes) and expose our own operator set (GqlOperators). This is the direct
  analog of WhereInput, just hand-rolled instead of generated. Good enough unless we
  want richer, per-field-type operators (e.g. string `contains`, only-comparable `gt`).
  -> Possible: make GqlOperators field-type-aware (contains/startsWith for strings,
     gt/gte/lt/lte only for number|string|Date), like Prisma's typed filters.
- INPUT types for queries/mutations: these are the resolver ARGS (we have ArgsOf).
  They matter for createCan's getSubjectData(args) typing, NOT for subject conditions.
  -> Possible: type getSubjectData's return as GqlConditionsFor<TMap[subject]> and its
     `args` param as ArgsOf<...> so arg-derived conditions are end-to-end typed.

"Taking in the gql schema" (runtime GraphQLSchema) — what it could buy us
-------------------------------------------------------------------------
Compile-time types already come from codegen, so we do NOT need the runtime schema
for typing. A runtime schema (or the codegen introspection) WOULD enable:
  [x] P1. DONE (2026-09) — validateGraphQLRules(schema, rules, options?) in
          src/validateGraphQLRules.ts. Kept separate from buildGraphQLAbility
          (whose options are CASL's) and shaped like validatePermissions: walks
          the rows, aggregates every problem into one PermissionsError, throws.
          Checks subject names (mirroring what SubjectName excludes: root op
          types, scalars; plus interfaces/unions, which __typename detection can
          never match), `fields` (skipping `*` patterns, which
          createMongoAbility's fieldPatternMatcher accepts), condition paths
          (following dotted paths through object-typed fields; stopping at a
          scalar/enum/union), the operator set CASL's mongoQueryMatcher knows
          (from @ucast/mongo's MongoQuery type; `$where` rejected), and the
          rule's shape. The shape check earned its place: a DB row with
          `inverted: "false"` is a DENIAL to CASL.
          THE CAVEAT that shaped the API: conditions name MODEL fields
          (ResolversTypes[K]), which diverge from schema fields under codegen
          `mappers`. So condition-field checking is on by default (fail loud)
          with `conditionFields: 'none'` as the opt-out; subjects and `fields`
          are schema names regardless and are always checked. Condition VALUES
          are not checked against field types — that is P2's territory.
          (Original ask: reject rules whose subject or condition fields don't
          exist in the schema when rehydrating DB-stored rules — high value for
          the DB-rules workflow where rules are edited outside the type system.)
  [ ] P2. A codegen-time generator that emits a typed condition map (per-field
          operator types) from the schema — closest to what @casl/prisma gets for free
          from Prisma's generator. Heavier; only if MongoQuery proves too coarse.
          NB (2026-08): the generated types would have to keep matching CASL's
          mongoQueryMatcher at runtime, since that is what actually evaluates the
          conditions. A generator can therefore only NARROW what MongoQuery
          already allows (e.g. drop $gt on booleans); it cannot add operators
          without also shipping a custom matcher, which forfeits interoperability
          with every other CASL tool. @casl/prisma escapes this by shipping its
          own matcher AND its own accessibleBy; matching that is a much bigger
          commitment than this entry implied when it was written.

Decision points for the user
----------------------------
1. Richer, field-type-aware operators (string contains/startsWith; comparable-only
   gt/lt) vs the current uniform operator set? (Serializability is preserved either way.)
2. Type getSubjectData against the schema (ArgsOf args -> GqlConditionsFor return)? —
   small, high-value, no runtime schema needed.
3. [ANSWERED: yes, done] Add load-time rule validation against a provided GraphQLSchema (P1)? This is the
   only part that actually needs "taking in the gql schema."
4. Is a codegen plugin (P2) in scope, or out (keep types purely inferred from the
   existing codegen output)?
