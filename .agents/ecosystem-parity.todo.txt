Wider GraphQL authz ecosystem — analysis (Workstream D)
=======================================================
Status: ANALYSIS ONLY. No code written. Ideas harvested from libraries OTHER
than graphql-shield, ranked by value to this library.

Companion file: shield-parity.todo.txt (the graphql-shield gap table).
Several items here matter MORE than shield parity does — E1 in particular.

[x] E1. POST-EXECUTION RULES — DONE (createCan.onResult). Authorizes the
        resolved value; lists are all-or-nothing; null passes through; requires
        a buildSubject tagger (throws at construction without one); REFUSES root
        mutation fields BEFORE calling the resolver, so the side effect never
        happens. Note the analysis below was wrong on one point: this needed NO
        architectural change and did NOT depend on E2 — the middleware shape
        already lets a rule await resolve() and then check. Side-effecting
        QUERIES remain undetectable and are documented as a caution.
        Still open from this item: masking a denied list ITEM instead of denying
        the field (see E4 / accessibleby.todo.txt).

[ ] E1-orig. POST-EXECUTION RULES — authorize the RESOLVED ENTITY, not the
        client-asserted args.
        Source: graphql-authz postExecRule / PostExecutionRule. Its rules get
        (context, fieldArgs, RESULT, parent).

        THE SINGLE MOST VALUABLE IDEA IN THIS SURVEY. It is the actual fix for
        the IDOR footgun that packages/graphql-casl/README.md documents as a
        known limitation and that test/example.test.ts already encodes as a
        passing test. graphql-middleware runs the rule BEFORE the resolver, so
        getSubjectData only ever sees what the CLIENT ASSERTED; a post-exec
        rule can run ability.can(action, typed('Todo', result)) against the
        REAL record. That is precisely what CASL conditions are built for, so
        the fit is unusually good.

        Carry over graphql-authz's own caveat verbatim: with post-exec rules the
        RESOLVERS STILL RUN even when the rule denies, so they are unsuitable
        for mutations and for queries with side effects (view counters etc.).
        graphql-authz's documented alternative for those cases is to query the
        DB inside a PRE-exec rule instead — worth documenting the same fork.

        Cross-links: accessibleby.todo.txt (row-level filtering is the natural
        sibling — deny a list ITEM vs. deny the whole field); E4 below (a denied
        item in a list wants masking, not a thrown error).

[!] E2. SELECTION-SET INJECTION — BLOCKED ON THE CHOSEN MECHANISM. See FINDING.
        FINDING (probed, 2026-08): graphql-middleware CANNOT deliver this.
        applyMiddleware extracts a rule's `fragment` into a
        `fragmentReplacements` ARRAY hung off the returned schema object, and
        does nothing further with it. Probe: a rule on User.email declaring
        `... on User { id }`, queried as `{ me { email } }` — Query.me's
        info.fieldNodes was still `me { email }`, no `id`. The array is only
        consumed by graphql-tools DELEGATION (v3-era mergeSchemas), not by plain
        execution, which is how this library's consumers run.
        Consequence: shipping a `fragment` option on `Rule` would be an unkept
        promise — exactly the silently-inert failure mode applyPermissions now
        rejects elsewhere. NOT SHIPPED, deliberately.
        Parent-aware field rules shipped WITHOUT it (createCan's getSubjectData
        now takes (args, parent)); the projecting-resolver hazard is documented
        instead of falsely guaranteed away.
        Real selection-set injection must happen BEFORE execution, i.e. as part
        of the envelop/Yoga plugin (E6). Re-scope this item there.

[ ] E2-orig. SELECTION-SET INJECTION — a rule declares the fields it needs, and they
        are fetched even if the client didn't request them.
        Source: graphql-authz `selectionSet: '{ status author { id } }'`;
        equivalently shield's `fragment` (see S5 in shield-parity.todo.txt).
        Two independent libraries converged on this, which is a strong signal.
        Was believed to be a prerequisite for BOTH E1 and parent-aware field
        rules. It was neither — both shipped without it. And the claim that
        "graphql-middleware already supports the {fragment, resolve} form" is
        true only of the TYPE; see the FINDING above for what it actually does.

[x] E3. DONE — createCan(...).fields(action, subject, getSubjectData?).
        Attached as a TYPE-level PermissionsMap entry, it checks
        ability.can(action, subject, info.fieldName) per field, so one CASL rule
        drives every field of the type. No schema-walk change was needed: a
        type-level entry already fans out to every field, and a Rule already
        receives info.fieldName.
        Subject defaults to the resolver's `parent` (falling back to the bare
        subject name on a root field, which has no parent); a buildSubject tagger
        is required. Deny-by-default across the type's fields, unlike the map.
        RESOLVES THE OPEN QUESTION BELOW: it sits ALONGSIDE hand-listed field
        rules, not replacing them — both are valid map entries and a per-field
        entry still wins by wildcard precedence.
        NOT used: permittedFieldsOf from @casl/ability/extra. It answers "which
        fields MAY I read", which is the tool for MASKING (E4), not for gating.
        Pick it up there.

[ ] E3-orig. CASL FIELD-LEVEL PERMISSIONS — can('read', 'Post', ['title']) and
        permittedFieldsOf from @casl/ability/extra.
        Not an ecosystem gap so much as UNUSED CAPABILITY IN A DEPENDENCY THE
        PROJECT ALREADY HAS. CASL's `fields` argument maps 1:1 onto GraphQL
        field selection. Nothing in src/ touches it today.
        Payoff: one ability rule could drive EVERY field rule for a type, instead
        of hand-listing them in the PermissionsMap — which is exactly the kind
        of schema-derived leverage this library is already built around.
        Pairs with E4 (mask the fields CASL says you may not read) and with E8
        (a type-level '*' whose behavior is "consult permittedFieldsOf").

[x] E4. DONE — applyPermissions(..., { maskDenials: true }).
        A denied field resolves to an empty value instead of raising an error:
        null for a nullable field, [] for a NON-NULL LIST (an empty list
        satisfies non-null, which is exactly the [Todo!]! case the integration
        test documents). A non-null field that is not a list has no value that
        satisfies it, so it still throws — masking is bounded by the schema, and
        that limit is documented rather than papered over.
        The nullability decision is made during the SCHEMA WALK, per field, so
        it costs nothing at request time. The mask is a factory, not a value: a
        shared [] would be handed to every request.
        Only DENIALS are masked. A rule that threw a bug of its own, and a
        resolver that failed on a permitted field, both still surface — masking
        those would report an outage as a permission decision. This is the same
        three-way failure classification the error-control options use
        (shield-parity S6-S9), reusing its denial marker.
        Follow-on: createCan's `onResult` and its `Not authenticated` now throw
        MARKED denials (denialFrom) rather than bare Errors, so they mask and
        take a fallbackError like every other denial.
        NOT taken from Pothos: `treatErrorsAsUnauthorized` (an error inside a
        rule counted as a denial) — that is the opposite of `debug`, which this
        library already ships, and it hides bugs.

[ ] E4-orig. UNAUTHORIZED -> null INSTEAD OF THROWING.
        Sources: Pothos `unauthorizedResolver` (return null / [] instead of an
        error) and `treatErrorsAsUnauthorized`; envelop generic-auth
        `rejectUnauthorized: false` (protected fields fail silently, public
        fields still execute).
        Here EVERY denial throws. test/integration/permissions.integration.test.ts
        already documents the resulting asymmetry: a denial on a nullable field
        (me: User) nulls just that field, but a denial under a non-null chain
        ([Todo!]!) nulls the ENTIRE data payload. Field-masking is the standard
        alternative and would make partial responses actually usable.

[ ] E5. DIRECTIVE-BASED DECLARATION — @can(action:, subject:) in SDL.
        Sources: graphql-authz @authz(rules:, compositeRules:,
        deepCompositeRules:) on FIELD_DEFINITION | OBJECT | INTERFACE;
        envelop generic-auth @authenticated / @skipAuth / @requiresScopes.
        The dominant idiom for schema-first users and the main reason someone
        picks graphql-authz over shield — permissions live next to the schema
        instead of in a parallel map.
        Fits this repo's existing shape as a THIRD package alongside
        graphql-casl-codegen. Note graphql-authz also supports attaching rules
        via `extensions` (code-first) and via a standalone `authSchema` object;
        PermissionsMap is already the equivalent of that third form.

[x] E6. NON-graphql-middleware INTEGRATIONS — envelop/Yoga plugin, Apollo
        Server plugin.
        graphql-authz ships plugins for Apollo Server, envelop, express-graphql,
        graphql-helix, Apollo Federation and schema stitching; it does this by
        wrapping `execute` (wrapExecuteFn) rather than mutating the schema.
        This is a REACH limitation, not a feature one: graphql-middleware is the
        sole integration path here and is awkward on Apollo Server 4+ and on
        federated gateways. An envelop plugin would likely widen the addressable
        audience more than any single shield feature would.
        Worth noting graphql-authz explicitly advertises "doesn't mutate the
        executable schema" as a benefit — applyPermissions does mutate it.

        DONE (2026-08) — shipped as packages/graphql-casl-envelop,
        `useGraphQLCasl({ permissions, ...applyPermissionsOptions })`.
          - Built on @envelop/on-resolve, NOT on wrapExecuteFn and NOT on
            graphql-middleware. That hook hands over each field's resolver as
            execution reaches it, which is what lets the same PermissionsMap run
            against a schema the host owns.
          - The permission SEMANTICS are not reimplemented: the runtime package
            grew `resolvePermissions(schema, map, options)` -> (type, field) =>
            Rule | undefined, and both applyPermissions and this plugin consume
            it. Wildcards, fallbackRule, error control and maskDenials cannot
            drift between the two integrations because there is one
            implementation.
          - Validation happens in onSchemaChange, so a bad map throws a
            PermissionsError while the server is being built rather than on the
            first query that touches the offending field. Swapped schemas are
            re-validated (both maps are keyed by schema in a WeakMap).
          - SHARP EDGE, verified in @envelop/on-resolve's source:
            `replaceResolver` mutates the field's resolver permanently, once —
            it is not a per-call wrapper. Wrapping on every resolution would
            nest the rule N deep. Guarded with a per-schema Set of
            "Type.field" keys.
          - Fields with no resolver of their own are still guarded: useOnResolve
            wraps the default resolver too, which is what makes canUser.fields
            work on a plain object type. Introspection is skipped by the hook.
          - This package is NOT zero-dependency: it depends on
            @envelop/on-resolve. Peers: @envelop/core >=5, graphql >=16,
            @vantreeseba/graphql-casl >=1.
          - Apollo Server plugin: NOT shipped. Apollo 4 has an envelop
            integration, so the plugin above already covers it; a separate
            Apollo-native package would be a second implementation for no new
            reach.
          - STILL OPEN, re-scoped here from E2/S5: selection-set injection. The
            plugin runs per RESOLVER, so it can wrap and it can mask, but it
            cannot add fields to the selection set the parent resolver sees.
            That needs an onExecute/document-level hook, not on-resolve.

[ ] E7. GRANTED SCOPES — a parent grants authorization to its children.
        Source: Pothos grantScopes / $granted. "$granted scopes are separate
        from other scopes" and do not inherit transitively.
        Avoids re-authorizing Post.author when Post itself was already
        authorized. Meaningful on nested and list-heavy queries, and it composes
        with the per-request cache from S4b.

[ ] E8. WILDCARD PRECEDENCE, PROPERLY SPECIFIED.
        If S3 (wildcards) gets built, copy graphql-authz's spec rather than
        shield's — it is strictly more complete:
          - '*' usable as a TYPE name and as a FIELD name, in any combination
          - wildcard rules NEVER compose with each other; exactly one applies
          - a wildcard is overridden by ANY explicitly attached rule
          - precedence: (1) any field of a NAMED type, (2) a NAMED field of any
            type, (3) any field of any type
        Shield only implements the per-type '*' field default.

[ ] E9. DENY-BY-DEFAULT AS A NAMED MODE.
        Source: envelop generic-auth modes — protect-all / protect-granular /
        resolve-only (plus @skipAuth to opt individual fields out of
        protect-all).
        Same machinery as S2 (fallbackRule), but the MODE framing is far more
        legible in docs than an options flag, and it makes the schema-coverage
        guarantee explicit rather than implicit. Recommend adopting the framing
        even if the implementation is just fallbackRule underneath.

[ ] E10. INTERFACE / UNION RULE INHERITANCE.
         graphql-authz attaches rules to INTERFACE types and inherits them to
         implementors (and Pothos has skipInterfaceScopes to opt out).
         Nothing in src/ is abstract-type aware: no __resolveType / __isTypeOf
         handling, no inheritance, no per-concrete-type resolution for union
         members. Subject detection is strictly the literal __typename string.
         SHARP EDGE (FIXED): __isTypeOf and __resolveType are keys of the
         generated per-type resolver interfaces and used to typecheck as rule
         targets in PermissionsMap. They are now Exclude'd from its field keys,
         so attaching a rule to one is a compile error. The rest of E10 —
         inheriting rules from an interface to its implementors — is untouched.

[ ] E11. TEST ESCAPE HATCH — disable authorization wholesale.
         Source: Pothos disableScopeAuth. Small, cheap, and consumers will
         otherwise hand-roll it badly (or worse, ship the hand-rolled version).

[x] E12. EXTERNAL PDP ESCAPE HATCH — OPA / Cerbos / OpenFGA / Oso.
         CASL cannot express relationship-derived (ReBAC / Zanzibar-style)
         permissions: "can edit any doc in a folder they own". This is the most
         common structural objection to a CASL-based approach.
         Rules are ALREADY async functions, so calling out to a policy decision
         point already works today. This is therefore a DOCUMENTATION task, not
         a code one — a worked example of a rule that awaits a PDP, plus a note
         on caching the decision per request (S4b), neutralizes the objection at
         essentially zero cost. Highest doc-value item in this file.

         DONE (2026-08) — README section "Delegating to an external policy
         engine". Documentation only, no code: a `rule()` check awaiting an
         OpenFGA-style check, composed with the ability-backed rules via
         `chain` so the network call runs last. Two points made explicitly
         because both are easy to get wrong:
           - a PDP OUTAGE IS NOT A DENIAL. A check that throws propagates
             unchanged rather than becoming Forbidden, so the example returns a
             string on a negative decision and never catches. Catching and
             returning false reports an unreachable service as "you may not".
           - cache the PENDING PROMISE per request, not the resolved value, so
             concurrent sibling fields share one round trip (S4b's shape).
         Also cross-linked accessibleBy: a PDP's list-objects endpoint plays the
         same role for list fields that accessibleBy plays for CASL rules.


EXPLICIT NON-GOALS (record so they stop being re-proposed)
---------------------------------------------------------
- Row/list-level filtering (accessibleBy): already tracked in
  accessibleby.todo.txt. graphql-shield doesn't do it either. E1 and E3 both
  brush against it — cross-link, don't duplicate.
- Query cost / depth / rate limiting: GraphQL Armor,
  graphql-query-complexity, graphql-depth-limit. Adjacent hardening, NOT
  authorization. Worth one README line pointing at them so the boundary is
  explicit, and nothing more.
- Database-layer RLS (Hasura, PostGraphile): different architecture entirely.

WHERE graphql-casl ALREADY LEADS (say this out loud in the docs)
---------------------------------------------------------------
None of graphql-shield, graphql-authz, Pothos scope-auth or envelop
generic-auth offer:
  - conditions evaluated against subject attributes (they all use opaque
    boolean predicates)
  - subject/field/condition names type-checked against the schema at compile
    time
  - permissions as plain serializable JSON, so they can live in a database and
    be rehydrated at startup
The gap analysis should be framed as "plumbing to catch up on, model to defend",
not as a pure deficit list.


OPEN QUESTIONS
--------------
- [ANSWERED] E1 (post-execution rules) is architecturally the biggest item here
  and cannot be done inside the current pre-resolver middleware shape without
  also doing E2. Is closing the documented IDOR gap worth that?
  Answer: the premise was false. A rule receives (resolve, parent, args, ctx,
  info) and can simply await resolve() before checking, so E1 shipped WITHOUT
  E2. E2 is still wanted, for parent-aware field rules.
- E5 (directives) and E6 (envelop plugin) are each a new package. Which, if
  either, is worth the maintenance surface for a solo-maintained project?
- [ANSWERED] E3: should CASL field-level permissions REPLACE hand-listed field
  rules in PermissionsMap, or sit alongside them as an alternative?
  Answer: alongside. `fields()` is just another rule, so a per-field map entry
  still overrides it by the normal wildcard precedence, and nothing existing
  had to change.
- E4: is null-masking a per-rule option, a global mode, or both?
