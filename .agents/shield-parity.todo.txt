graphql-shield feature parity — analysis (Workstream C)
=======================================================
Status: ANALYSIS ONLY. No code written. This file is the gap table plus a
prioritized backlog; nothing here is scheduled yet.

Companion file: ecosystem-parity.todo.txt (graphql-authz / Pothos / envelop
ideas, which in several places matter MORE than shield parity does).

Sources
-------
Verified against graphql-shield's SOURCE, not its docs site (the-guild.dev/
graphql/shield/docs/api 302s to the GitHub repo). Repo: maticzav/graphql-shield,
packages/graphql-shield/src/{types,constructors,rules,generator,shield,
validation}.ts.

Motivation
----------
graphql-casl and graphql-shield occupy the same niche: a graphql-middleware
permission layer. Shield is the incumbent most users would migrate FROM, so its
feature list is the de-facto baseline.

Where graphql-casl is clearly AHEAD, and should keep saying so:
  - CASL conditions on subjects (shield rules are opaque predicates)
  - schema-derived typed subjects; compile-time validation of type / field /
    subject / condition-field names (stronger than shield's runtime check)
  - JSON-serializable rules for DB-backed, cached-at-startup permissions

Where it is behind is the RULE PLUMBING around that model. src/rules.ts is ~103
lines: a `Rule` type alias, `accept`, `deny`, `PermissionsMap`, and an
`applyPermissions` that is a single cast into applyMiddleware. Shield's
equivalent layer carries ~16 features this has no answer for.


MIGRATION GUIDE — DONE (2026-08)
--------------------------------
README section "Coming from graphql-shield": the shield-concept -> here table
(constructors, combinators, options, validation), the three things that differ
enough to bite, and a worked before/after showing what the port buys.
The one that MUST stay documented: allowExternalErrors defaults to TRUE here and
FALSE in shield, so a map ported verbatim starts leaking resolver errors that
shield was masking. Also recorded there: `deny` rejects rather than throwing
synchronously (every rule() rule is async), and there is no `fragment` option
(S5 — the option cannot keep its promise under graphql-middleware).
Still absent and named as absent rather than papered over: per-rule caching
(S4b), inputRule (S11).


TIER 1 — structural (no workaround exists today)
------------------------------------------------

[x] S1. DONE, via the additive CheckableRule design below. `rule(check, {name})`
        wraps a predicate; and/or/not/chain/race combine them. and+chain throw
        the first failure, or+race the last; and+or evaluate in parallel,
        chain+race short-circuit. Non-checkable operands (hand-written
        middleware, createCan(...).onResult) are rejected at CONSTRUCTION time,
        naming the operand's position. createCan's pre-execution rules are now
        CheckableRules, so they compose. Errors raised INSIDE a check propagate
        rather than becoming denials (see S9).
        Behaviour change worth noting: `deny` now rejects rather than throwing
        synchronously, since every rule() rule is async. Equivalent under
        graphql-middleware, which awaits.

[ ] S1-orig. LOGIC COMBINATORS: and / or / not / chain / race.
        Shield: constructors.ts + rules.ts (RuleAnd/RuleOr/RuleNot/RuleChain/
        RuleRace). `and`/`or` evaluate in parallel; `chain`/`race` sequentially
        (chain = short-circuiting and, race = short-circuiting or);
        `not(rule, error?)` takes an optional custom error.
        Here: absent, and UNBUILDABLE against today's `Rule`. A `Rule` is a
        wrapping middleware (resolve, parent, args, ctx, info) that denies by
        THROWING — there is no way to ask it "would you pass?" without letting
        it run the resolver. See DESIGN DECISION below.

[x] S2. DONE (applyPermissions options.fallbackRule). fallbackRule (whitelist mode).
        Shield: shield.ts normalizeOptions defaults it to `allow`; setting
        `fallbackRule: deny` is how you get deny-by-default across a schema.
        Here: absent. Any type/field NOT named in the PermissionsMap is
        silently UNGUARDED — implicit allow-all.
        NB for the README: the "deny by default" claim there is about CASL
        ABILITIES, not about schema coverage. Those are different guarantees
        and the docs currently blur them.

[x] S3. DONE (graphql-authz precedence, both positions). Wildcard '*' key.
        Shield: generator.ts applyRuleToType pulls rules['*'] as the per-type
        default, strips it, then validates the remaining keys against the
        schema's field map.
        Here: absent, and would not typecheck (PermissionsMap keys are
        `keyof TResolvers`). See E8 in ecosystem-parity.todo.txt — graphql-authz
        specifies wildcard precedence better than shield does; copy that spec,
        not this one.

[ ] S4. RULE RESULT CACHING: cache: 'no_cache' | 'contextual' | 'strict' |
        ICacheKeyFn, plus a `hashFunction` option.
        Shield: rules.ts Rule#executeRule. 'contextual' keys on the rule name
        alone; 'strict' keys on hash({parent, args}); a function gets the raw
        (parent, args, ctx, info). Cache lives at ctx._shield.cache.
        Here: absent; nothing memoizes.
        CONCRETE COST: createCan awaits getAbility(context) on EVERY guarded
        field resolution, so a query touching 50 nodes rebuilds the ability 50
        times unless the consumer memoizes it themselves.

        [x] S4a. DONE. createCan now memoizes getAbility(context) in a
                 WeakMap<object, Promise<AbilityLike>> created per factory, so
                 every rule from one createCan shares a request's ability. A
                 rejected build is evicted so it can't poison the rest of the
                 request; a non-object context falls back to no memo.
        [x] S4b. DONE (perf-caching pass, 2026-09-03). General rule caching,
                 ZERO-DEP: rule(check, { cache }) with 'no_cache' | 'strict' |
                 'contextual' | (parent, args, ctx, info) => key. The custom
                 key function is the escape hatch instead of shield's
                 `hashFunction` — shield keys `${name}-${key}` in
                 ctx._shield.cache; here the key selects a slot in the rule's
                 own per-request WeakMap, and `undefined` means "skip the
                 cache for this call". 'strict' uses a sorted-key JSON
                 stringifier (empty args short-circuit to ''; unkeyable args
                 such as BigInt/circular run uncached rather than throw).
                 The cache is NOT on the context at all (neither a string key
                 nor a Symbol): each rule owns a WeakMap<context, ...>, so
                 nothing can collide with app context fields and there is no
                 per-rule-name collision either (shield needs unique names;
                 we don't — see S14). createCan rules accept the same option
                 as a 4th argument. See .agents/perf-pass.todo.txt for the
                 measurements.

[!] S5. FRAGMENTS — WON'T SHIP VIA graphql-middleware. See the FINDING under E2
        in ecosystem-parity.todo.txt: the fragment never reaches execution, so
        the option would promise a guarantee it cannot keep. Parent-aware field
        rules shipped without it. Re-scope to the envelop plugin (E6).

[ ] S5-orig. FRAGMENTS: rule({ fragment: '... on User { id }' }).
        Shield: generator.ts emits the {fragment, resolve} /
        {fragments, resolve} middleware form when a rule declares one, forcing
        the fields a rule needs into the parent's selection set.
        Here: UNREACHABLE. graphql-middleware supports this
        (IMiddlewareWithOptions, node_modules/graphql-middleware/dist/
        types.d.ts), but `Rule` is typed as the bare function form only.
        This is the missing piece behind packages/graphql-casl/TODO.md item 2
        ("parent-aware createCan"): a parent-conditioned field rule can't be
        trusted unless the fields it reads are guaranteed to be selected.
        Same mechanism as E2 in ecosystem-parity.todo.txt, arriving from a
        different direction — do these together.


TIER 2 — error control
----------------------

[~] S6. PARTLY DONE. A `rule()` check returns boolean | string | Error, and an
        Error is thrown as-is — so a check CAN now carry a GraphQLError with
        extensions and a code. What is still missing is the surrounding error
        CONTROL: fallbackError (S7), masking (S8), debug (S9), CASL reason (S10).
        createCan still denies with a hardcoded Error('Forbidden').

[ ] S6-orig. Rules return boolean | string | Error (IRuleResult).
        Shield: rules.ts Rule#resolve normalizes string -> new Error(string).
        Here: rules must THROW. No per-rule custom message, no GraphQLError
        with extensions / error code.

[x] S7. DONE — applyPermissions options.fallbackError, same three forms as
        shield (Error | string | mapper receiving (original, parent, args, ctx,
        info)). Replaces ONLY denials that did not name their own error; an
        explicit string/Error from a check, or a CASL reason, survives it.

[ ] S7-orig. fallbackError: Error | string | mapper.
        Shield: IFallbackErrorMapperType = (err, parent, args, ctx, info) =>
        Error | Promise<Error>. Default new Error('Not Authorised!').
        Here: denial messages are hardcoded plain Error('Forbidden') /
        Error('Not authenticated') with no extensions or codes.

[~] S8. DONE, WITH THE OPPOSITE DEFAULT TO SHIELD. options.allowExternalErrors
        defaults to TRUE here (resolver errors reach the client), where shield
        masks by default. Rationale: masking is safer, but it is not 1.0
        behaviour and silently swallowing resolver errors on upgrade is worse
        than an explicit opt-in. Documented in the README and to be repeated in
        the migration table (see OPEN QUESTIONS). REVISIT AT 2.0 — masking is the
        better default for a fresh major.

[ ] S8-orig. allowExternalErrors.
        Shield: generator.ts wraps rule + resolver execution in try/catch; by
        DEFAULT it MASKS resolver-thrown internal errors behind fallbackError,
        and allowExternalErrors: true passes them through.
        Here: there is no try/catch anywhere in the library, so internal errors
        leak verbatim. Note this is a security-relevant default difference:
        shield fails closed, graphql-casl fails open.

[x] S9. DONE — options.debug rethrows an error raised INSIDE a rule instead of
        reporting it as a denial. This needed a way to tell three failures apart:
        rule() now marks the errors it throws as denials (a non-enumerable
        Symbol.for('graphql-casl.denial') carrying 'default' | 'explicit'), and
        resolver errors are identified by capturing what the wrapped resolve
        threw. Anything left over is a rule failure.

[ ] S9-orig. debug.
        Shield: debug: true RETHROWS errors raised INSIDE a rule instead of
        quietly converting them to a denial.
        Here: absent. A throwing getAbility() is today indistinguishable from a
        legitimate denial, which is a genuinely annoying thing to debug.

[x] S10. DONE — a cannot(...).because('...') reason becomes the denial message,
         on both the pre-execution and onResult paths. Read via
         ability.relevantRuleFor(action, subject)?.reason rather than
         ForbiddenError.from(ability).throwUnlessCan(), because the latter also
         rewrites the DEFAULT message to `Cannot execute "x" on "Y"` — which
         both changes this library's denial message and discloses a schema type
         name to an unauthorized caller.

[ ] S10-orig. (CASL-side, shield-adjacent) rule `reason` plumbing.
         createCan calls ability.can(...), not
         ForbiddenError.from(ability).throwUnlessCan(...), so per-rule `reason`
         strings set on the ability are silently discarded. Pairs naturally
         with S6/S7 — reason is the obvious source for a denial message.


TIER 3 — smaller
----------------

[x] S11. inputRule — argument validation as a rule.
         SHIPPED 2026-09-04 as `validateArgs(schema, { replace? })` in
         src/validateArgs.ts, on Standard Schema as recommended below: the
         spec's `StandardSchemaV1` interface is vendored, so zod / valibot /
         arktype / yup>=1.7 all work and the package stays zero-dep. The
         resolver receives the parsed output as `args` (`replace: false`
         validates only). A failure is a `GraphQLError` with
         `extensions.code: 'BAD_USER_INPUT'` and `extensions.issues`, marked
         as an EXPLICIT denial so `fallbackError` leaves it alone and
         `onDeny: 'filter'` keeps its code; a validator that throws is a rule
         failure. Plain `Rule` (rewrites args), so composed via `wrap`, not
         the combinators. No `cache: 'strict'` — validation is per call by
         nature, and the args are the input.
         Shield: constructors.ts inputRule + rules.ts InputRule, backed by yup,
         forced to cache: 'strict'.
         Here (before): absent; `args` was an unchecked `args as TArgs` cast.
         If built: prefer Standard Schema (standardschema.dev, the `~standard`
         property) over a yup dependency — zod / valibot / yup>=1.7 all
         implement it, so consumers bring their own validator and the package
         stays zero-dep.

[ ] S12. Whole-schema rule: shield(someRule) applies one rule to every field.
         Shield: generator.ts applyRuleToSchema.
         Here: absent; PermissionsMap must be keyed per type.

[x] S13. DONE (PermissionsError aggregates every problem). RUNTIME validation.
         Shield: generator.ts throws ValidationError naming the types/fields
         that don't exist in the schema ("It seems like you have applied rules
         to X.y fields but Shield cannot find them in your schema.").
         Here: compile-time only, via `keyof TResolvers` — and only if the
         consumer uses codegen. Overlaps prisma-schema-typing.todo.txt item P1
         (validating rehydrated DB-stored rules against a runtime
         GraphQLSchema); do them as one piece of work.

[ ] S14. Duplicate rule-name validation (validation.ts validateRuleTree —
         errors if two rules share a name but aren't the same function).
         N/A today because rules are anonymous. Becomes relevant the moment
         rules get names for caching (S4b).

[x] S15. DONE (free — graphql-middleware already skips them, and the walk
         skips them too). Introspection-type exclusion (isIntrospectionType) when applying
         rules broadly. Becomes REQUIRED the moment S2 or S3 exists, otherwise
         a fallbackRule would guard __Schema / __Type and break introspection.

[x] S16. DONE — accept/deny are CheckableRules built with rule().

[ ] S16-orig. allow / deny usable as combinator operands.
         Here: accept / deny exist and behave correctly, but they're plain
         middleware, so they cannot be operands of S1's combinators. Falls out
         of the DESIGN DECISION below for free.


DESIGN DECISION (recorded — do not relitigate) — NOW IMPLEMENTED
----------------------------------------------------------------
Shipped as described, with two deviations: `fragment` was dropped from the
options (it cannot work — see the FINDING under E2 in ecosystem-parity), and
`cache` was deferred to S4b (since shipped — see S4b). Otherwise as written.

For S1, the user chose the ADDITIVE `CheckableRule` approach over redefining
`Rule` as a shield-style predicate:

  export type RuleResult = boolean | string | Error;
  export type Check =
    (parent, args, context, info) => RuleResult | Promise<RuleResult>;

  export interface CheckableRule extends Rule {   // still callable as middleware
    readonly check: Check;
    readonly ruleName: string;
    readonly fragment?: string;
  }

  export function rule(check: Check, opts?: {
    name?: string;
    cache?: 'no_cache' | 'contextual' | 'strict' | ((p, a, c, i) => string);
    fragment?: string;
  }): CheckableRule;

Rationale:
  - Existing hand-written middleware `Rule`s keep compiling and working, so no
    major version bump. The predicate-only alternative is breaking: accept/deny
    signatures change and every hand-written Rule stops compiling.
  - createCan's body is ALREADY a pure predicate (isAuthenticated +
    ability.can), so lifting it to CheckableRule is mechanical, and it then
    gains composition, caching and error control for free.
  - Combinators reject a non-checkable operand LOUDLY at construction time,
    naming the operand — never degrade silently.
  - accept/deny become CheckableRules, which resolves S16.
Honest cost: two rule kinds coexist, and the docs have to explain when you get
which. Accepted.

Semantics to implement when built: check() true -> resolve; false -> throw the
effective fallback error; string -> new Error(string); Error -> throw it.
