GraphQLAbility — redesign  (DONE)
=================================
Replaced the untyped ability (AppAbility + abilityOptions) with a schema-typed
one: a CASL MongoAbility whose conditions are checked against each subject's
fields. See the CORRECTION below — an intermediate bespoke-conditions design was
tried and dropped, and this file used to describe it as shipped.
Workstream B (accessibleBy-style row/list filtering) is in accessibleby.todo.txt.

CORRECTION (2026-08): this file previously described a BESPOKE conditions
language (GqlOperators / GqlFieldCondition / GqlConditionsFor / GqlConditions /
gqlConditionsMatcher). That was an intermediate design and NONE of it exists.
Those symbols were deleted when the custom matcher was replaced by CASL's own
`mongoQueryMatcher`, which `createMongoAbility` bundles. `GraphQLAbility` is a
CASL `MongoAbility` and conditions are CASL's standard mongo-query operators.
Anything downstream that builds on the bespoke language — notably P2 in
prisma-schema-typing.todo.txt — is building on something that is not there.

What shipped
------------
- src/graphqlAbility.ts:
    GraphQLAbility<TMap>        — CASL `MongoAbility` whose conditions are typed
                                  per subject, plus __typename detection.
    GraphQLAbilities<TMap>      — ability-tuple union; objects tagged with a required
                                  __typename; includes a [Action,'all'] member.
    createGraphQLAbility<TMap>()— typed AbilityBuilder over createMongoAbility;
                                  build() applies __typename detection (the mongo
                                  conditions matcher is built in).
    buildGraphQLAbility(rules)  — rehydrate an ability from stored JSON rules.
    GraphQLRule<TMap>           — serializable rule type (RawRuleOf).
    GraphQLAbilityOptions<TMap> — the options build()/buildGraphQLAbility accept.
  Conditions are CASL's mongo-query operators ($eq/$ne/$in/$nin/$gt/$gte/$lt/
  $lte/…), typed against each subject's fields via MongoQuery<TMap[K]>. They are
  plain JSON, so rules round-trip through a database unchanged.
- src/ability.ts: removed AppAbility + abilityOptions (untyped path GONE); kept
  Action/Actions; AbilityLike loosened to `can(...args:any[])` so a strictly-typed
  ability satisfies it. createCan casts to AbilityLike at the internal can() call.
- src/subjects.ts: createTyped now tags a required, narrowed __typename only
  (no __caslSubjectType__).
- Exports updated in src/index.ts.
- Tests migrated off MongoAbility/abilityOptions; new test/graphqlAbility.test.ts
  covers conditions, operators, manage/all, deny-by-default, and JSON round-trip
  rehydration via buildGraphQLAbility.
- Docs: README (Concepts, Conditions section, sections 1-5 incl. Persisting rules),
  AGENTS.md (structure + conventions). example.md added (minimal, comment-free).

KEY TECHNICAL FINDINGS
----------------------
1. CASL's TaggedInterface (types.d.ts) natively accepts `{ readonly __typename: T }`
   as a subject tag — alongside __caslSubjectType__ and `kind`. So __typename works
   for BOTH the AbilityBuilder's string-subject condition narrowing AND check-time
   can(). The catch: the tag must be REQUIRED. Codegen emits `__typename?:` (optional),
   which does NOT satisfy TaggedInterface<string> (`__typename: string` required) — that
   is why bare Partial<Model> tuples don't narrow. createTyped + the Tagged<> helper
   force a required __typename.
2. Per-subject condition typing through CASL's AbilityBuilder needs the Conditions
   generic to be an HKT — a plain conditions type makes ProduceGeneric fall back to
   the bare type and conditions stop narrowing. MongoAbility already ships that
   HKT (MongoQuery is declared with CASL's Container/produce machinery), which is
   the main reason the bespoke language was dropped: it was reimplementing this.
3. A strictly-typed Ability does NOT satisfy a `can(action:string,subject:unknown)`
   shape (variadic union overload vs fixed params) — hence AbilityLike was loosened.

InferSubjects — considered, NOT used
------------------------------------
CASL's InferSubjects<T> builds `T | TagName<T>` (object-or-name unions) from classes/
tagged interfaces. We already have a SubjectMap (name -> model) from codegen, so the
mapped tuple `{ [K]: [Action, Tagged<K,TMap[K]> | K] }[keyof TMap]` is more direct and
keeps everything derived from the generated types. Revisit only if we ever accept
class-based subjects instead of a SubjectMap.
